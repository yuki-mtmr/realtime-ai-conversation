# 合成ユーザーによるリリース前検証：研究方針と進め方

2026年11月19日 · @matt

関連資料: [synthetic-user-research.md](./synthetic-user-research.md)（先行調査メモ）、[synthetic-user-research-protocol.md](./synthetic-user-research-protocol.md)（進め方の規約）、[synthetic-user-research-plan.md](./synthetic-user-research-plan.md)（研究計画・具体版）

## 概要

公開データで「部品ごとの妥当性」を先に検証し、その結果を根拠にA社（国内旅行会社）の社内データでの本検証を申請する、二段構えで進める。

- **現在地**：統計とNemotronで作ったペルソナにアプリを操作させ、感想を集計・グラフ化できる段階。人間の実測値と突き合わせる仕組みはまだない。
- **本資料の目的**：(1) 数値化する行動指標を定める (2) 社内データにアクセスする前にできる検証手順を定める (3) 社内データ申請の根拠と内容を定める。
- **位置づけ**：合成ユーザーは実ユーザーテストの代替ではなく、リリース前に大きく外れた案を落とす絞り込み（スクリーニング）手段として検証する。

**新規性**：先行研究はEC・Web施策が中心で、旅行アプリの画面操作を人間の離脱データと照合した研究は見当たらない。離脱条件を持つペルソナ、新規アプリへの移植、モデルをまたいだ補正も未検証であり、本研究の検証対象とする（「研究の位置づけと展開」参照）。

## 現在地

合成ユーザーを動かす仕組みはできている。定量検証できない理由は、出力が自由記述で、比べる相手（人間の実測値）がないことにある。

| 要素 | 構築済みの内容 | 定量化に向けた課題 |
|---|---|---|
| ペルソナ | A社の過去の顧客統計（集計値）と Nemotron-Personas-Japan を突き合わせ、A社顧客の構成に合わせて抽出 | 属性の分布は現実に沿うが、行動データの裏づけがない。Nemotronは国勢調査の人口統計の分布に基づく合成データ |
| 実行 | ペルソナを持つエージェントがリリース前アプリを実際に画面で操作 | 操作ログを数値として残していない |
| 出力 | 感想を集計し、グラフ化するskill | 自由記述は人間の実測値と突き合わせにくい |
| 検証 | 定性評価のみ | 正解（人間の行動や結果）が手元にない |

> **注意点**：先行研究では、属性情報だけのペルソナは申込みの勝敗予測でペルソナなしを下回った（方向一致率0.30、ペルソナなしは0.65。クリック予測では逆に0.65対0.45で上回った）。現在のペルソナはこの「属性ベース」に近い（出典）。

## 数値化できる行動指標

感想に加えて、操作ログから数値を必ず出力する。分類はユーザビリティの国際規格ISO 9241-11の3要素（有効さ・効率・満足度）に合わせる。

| 要素 | 指標 | 定義 | 人間との比べ方 |
|---|---|---|---|
| 有効さ | タスク完了率 | 指定タスク（例：宿を探して予約確認画面まで進む）を完了した割合 | 完了率の差 |
| 有効さ | 離脱画面 | 完了せずに止めた画面とその割合（ファネル） | 画面ごとの離脱分布の距離 |
| 有効さ | 行き詰まり回数 | エラー表示、同じ操作の繰り返し、意図しない画面への遷移 | 件数の差、発生画面の一致 |
| 効率 | 操作数 | 完了までのクリック・入力・スクロールの回数 | 分布の距離 |
| 効率 | 戻る・やり直し回数 | 前の画面へ戻った回数 | 分布の距離 |
| 効率 | 検索・絞り込みの利用 | 検索語の変更、絞り込み、並べ替えの回数 | 操作種別の構成比 |
| 満足度 | タスクごとのやりやすさ | タスク直後に1問で7段階で答えさせる | 平均とばらつき |
| 満足度 | SUS（System Usability Scale） | 10問の標準質問紙、0〜100点 | 平均とばらつき |
| 選好 | 2案比較の選択率 | A案・B案を並べてどちらを選ぶか | 勝敗の方向一致率 |
| 問題の検出 | 指摘された問題の一致 | 感想を画面ごとの問題に分類した件数 | 人間が見つけた問題のうち何割を見つけたか（再現率） |

### 人間と比べるときの判定の種類

- **方向一致率**：2案のどちらが勝つかが人間の結果と一致した割合。A/Bテストの予測に使う。
- **分布の距離**：操作数や離脱画面の分布が人間とどれだけ違うか（例：Jensen–Shannon距離）。行動の人間らしさの検証に使う。
- **ばらつきの比**：合成ユーザー集団の標準偏差÷人間の標準偏差。NN/gの比較では、合成回答のばらつきは人間よりずっと小さかった（出典）。

既知の差として、Amazonの検証では1セッションの平均操作数が人間約16、エージェント約6で、エージェントは探索が少ない（出典）。操作数は差が出る前提で扱う。

## 肉付けの手順（社内データに触れる前まで）

公開データで2つの部品（ペルソナの構成、行動の人間らしさ）と方法そのものを2案比較で検証し、最後に社内の小規模テストでA社アプリ上の再現性を確かめる。各段階の合格基準は着手前に固定する。

### 準備：操作ログの形式を固定する

- 既存skillに、操作1回ごとの記録（ペルソナID、タスクID、画面名、操作種別、時刻、完了/離脱）をJSONで書き出す処理を足す。
- 操作種別は trivago データの分類（検索、絞り込み、並べ替え、詳細閲覧、予約サイトへの遷移など）に対応づけておく。後で社内ログと突き合わせるときの変換表になる。
- 感想は自由記述のまま残し、別途「画面×問題の種類」に分類した表を作る。
- **成果物**：ログ形式の定義書、1タスク分のサンプルログ。

### 段階1：ペルソナの構成を公的統計と照合する

- **使うデータ**：観光庁「旅行・観光消費動向調査」（日本人の旅行の年代・旅行種別・支出の分布）。
- **やること**：生成したペルソナ集団の年代・同行者・旅行目的の分布を、公的統計とA社集計値の両方と比べる。
- **確認すること**：A社顧客が日本人旅行者全体とどう違うかを説明できること。違いが大きい属性が、後で社内データを求める理由になる。
- **成果物**：属性ごとの分布比較表、ずれが大きい属性の一覧。

### 段階2：2案比較の方向一致率を測る（方法の検証）

- **使うデータ**：Upworthy Research Archive（実際に行われた見出しA/Bテストとそのクリック結果）。
- **やること**：同じテストの2案を合成ユーザーに提示し、どちらを選ぶかを集計する。実際に勝った案との一致率を、ペルソナなし・属性のみペルソナと比べる。
- **目安**：先行研究ではプロンプトだけのLLMの予測精度は65%以下にとどまる。これを有意に上回れないなら、ペルソナ設計を見直す。
- **注意**：見出しのクリックは旅行アプリの操作とは違う。ここで証明できるのは「2案比較という測り方が機能するか」まで。
- **成果物**：条件別の方向一致率と信頼区間。

### 段階3：操作の人間らしさを検証する（行動の検証）

- **使うデータ**：trivago RecSys Challenge 2019（宿検索サイトの実セッションログ）、OPeRA（ペルソナ付きの実ユーザーウェブ操作ログ）。
- **やること**：trivagoでは、人間のセッション長、操作種別の構成比、絞り込み利用率を分布として集計し、類似の宿検索タスクでの合成ユーザーの分布と比べる。OPeRAでは、ペルソナあり・なしで次の操作の予測精度が変わるかを確かめる。
- **確認すること**：操作数が少なく探索が浅いという既知の偏りがどの程度あるか。偏りを補正する指示や行動例をペルソナに与えたとき、分布が近づくか。
- **成果物**：分布の距離（補正前後）、偏りの一覧。

### 段階4：社内の小規模テストで、A社アプリ上の再現性を確かめる

- **対象**：社員5〜8名に、合成ユーザーと同じタスクを同じリリース前アプリで行ってもらう。顧客データは使わない。
- **やること**：完了率、離脱画面、操作数、指摘された問題の一致（人間が見つけた問題のうち何割を合成ユーザーが見つけたか）を比べる。
- **注意**：社員は顧客ではない。ここで確かめるのは「同じ画面で同じ問題を拾えるか」で、顧客層ごとの差は社内データで確かめる。
- **成果物**：人間と合成ユーザーの指標対照表、問題の再現率。

## ペルソナの定義と、人間の離脱統計への近似

検証する本体はペルソナ付きAIテスト全体で、比べる単位は個人ではなく集団である。「合成ユーザー集団の画面ごとの離脱分布」を「人間の離脱分布」に近づけ、補正に使っていない画面やバージョンで当たるかを確かめる。以下は先行研究を踏まえた設計案であり、この手順自体が実証されているわけではない。

### ペルソナの4層と必要なログ

離脱を再現するには、属性だけでなく「何をしに来て、いつ諦めるか」まで定義する。

| 層 | 決めること | 必要なログ（集計値でよい） | ログの出どころ | 現状 |
|---|---|---|---|---|
| 1. 構成 | どんな人が、どの割合で来るか | 年代・居住地、予約の同行者構成・旅行目的、利用デバイス | 会員データ、予約データ | 済（統計＋Nemotron） |
| 2. 来訪意図 | 何をしに来たか（予約したい／比較中／眺めるだけ） | 流入元と検索語、最初に開いた画面、検索条件の具体性（日付・人数・行き先の指定有無）、過去の訪問回数 | アクセス解析のイベントログ | 未 |
| 3. 行動傾向 | どう動くか（比較する件数、価格への敏感さ） | 検索回数、絞り込み・並べ替えの利用、閲覧した宿の数、価格帯の変更、戻る回数 | アクセス解析のイベントログ | 未 |
| 4. 離脱条件 | いつやめるか | 最後に見た画面、離脱直前の出来事（価格表示、空室なし、検索結果0件、ログイン要求、エラー）、後日戻って予約したか | イベントログ、予約データ | 未 |

層2と層4が特に重要。人間の離脱の多くは「最初から予約する気がなかった」人によるが、AIに「予約して」と指示すると全員が予約しに行く。またLLMは与えられたタスクを完遂しようとするので、やめてよい条件を明示する。

### 各層の先行研究との対応

4層の枠組み自体は先行研究にそのままの形ではなく、各研究の要素を組み合わせた設計案である。層1〜3は先例があり、層4は未検証の仮説として扱う。

| 層 | 先例 | 裏づけ |
|---|---|---|
| 1. 構成 | Agent A/Bは属性の分布を指定して生成。SimGymは類型ごとに重みを付けて再現 | ○ |
| 2. 来訪意図 | SimGymは本番の操作データから購入者像と意図を抽出し、意図とペルソナを組み合わせてプロンプトを作る | ○（1研究） |
| 3. 行動傾向 | SimGymは滞在・操作数、閲覧の深さ、検索行動、ファネルの進み方でセッションを分類。Amazon研究も行動データからペルソナを作成 | ○ |
| 4. 離脱条件 | SimGymの終了条件は目標達成・手数の上限・安全装置で、人間らしく諦める条件ではない。セッション終了を次の行動として予測する研究はあるが、ペルソナに持たせる方式ではない | △〜✗（本研究の仮説） |

「LLMはタスクを完遂しようとして諦めにくい」も検証済みの事実ではなく推測である。「離脱条件を明示したペルソナは人間の離脱分布に近づくか」は、trivagoのデータで比較実験として検証できる研究課題になる。

### ペルソナのデータ形式

ペルソナはモデルの重みではなく、プロンプトに渡すテキスト（構造化したJSONなど）として持つ。行動データペルソナも、ログの集計から作ったテキストに過ぎないため、現在のskillの仕組みのまま実行できる。

```json
{
  "id": "family-compare-01",
  "weight": 0.12,
  "layer1_composition": {"age": "30代", "companions": "夫婦と未就学児1人", "device": "スマートフォン"},
  "layer2_intent": "来月の週末に温泉宿を探している。今日は候補を絞るだけで、予約は家族と相談してから",
  "layer3_behavior": {"compare_items": "4〜6件", "price_sensitivity": "高い", "uses_filters": ["子連れ可", "価格帯"]},
  "layer4_exit": ["検索結果が3件未満", "合計金額が予算を2割超える", "会員登録を求められる"]
}
```

- 重み（weight）は、その類型が人間の利用者全体に占める割合。結果の集計時に使う。
- 1人の個人を再現するのではなく、集計から作った「類型」として持つ。個人情報を含まないので、申請でも扱いやすい。
- 重みを変える方式（ファインチューニング）もあるが、先行研究の主流はテキストであり、まずは不要。
- skillの構成案：ペルソナ生成（集計ログ→類型→JSON）、実行（ペルソナ×タスク）、集計（重み付きファネル）、評価（人間との距離）の4つ。

### ログからskillまでの流れ

類型と比率は数値の表であり、それを文章に変換したものがペルソナJSONになる。モデルに合わせるのは最後の補正だけで、それ以前はモデルを替えても使い回せる資産である。

```
① 人間のログ（DB・CSV）
      ↓ 集計
② 特徴量の表（セッション×特徴量のCSV）
      ↓ クラスタリング
③ 類型の統計 types.json        ← 数値のみ。モデル非依存【資産】
      ↓ テンプレートで文章化
④ 初期ペルソナ persona_base/    ← 自然文。ほぼモデル非依存【資産】
      ↓ モデルごとに補正
⑤ 補正済みペルソナ persona/{モデル名}/  ← モデル依存【モデル更新で作り直す】
      ↓
⑥ skillで実行 → 重み付きファネル集計 → 人間との比較
```

③と④の違い：

```jsonc
// ③ 類型の統計（数値）
{"type": "C2", "weight": 0.18, "compare_items_median": 5,
 "price_filter_rate": 0.72, "reached_detail_rate": 0.64, "session_end_at": "料金画面"}

// ④ 初期ペルソナ（文章）
{"type": "C2", "weight": 0.18,
 "behavior": "4〜6件の宿を比較してから決める。価格帯で絞り込むことが多い",
 "exit": "合計金額を見て予算を超えていたらやめる"}
```

| skillに入れるもの | 役割 | モデル更新時 |
|---|---|---|
| types.json | 類型の統計と比率 | そのまま |
| ③→④の変換スクリプトとテンプレート | 数値を文章にする | そのまま |
| persona_base/ | 初期ペルソナ | そのまま |
| ④→⑤の補正スクリプト | 人間とのずれを見て文章を直す | そのまま再実行 |
| persona/{モデル名}/ | 補正済みペルソナ | 作り直す |
| 実行・集計・評価の部分 | 画面操作、重み付き集計、人間との距離 | そのまま |

### ログが欠けたときにどこまでできるか

計画が成り立つかを決めるのは、画面遷移と終了のイベントログと、過去のA/Bテスト結果の2つ。層2はもともとログに直接は残らず、行動から推定する前提である。

| 欠けるもの | 影響 | 計画への影響 |
|---|---|---|
| 層1（会員属性） | 顧客層ごとの比較ができない | 小。行動の類型だけで進められる |
| 層2（意図の手がかり） | 序盤の画面の離脱率が合わない | 小。比較の起点をずらす |
| 層3・4（画面遷移と終了のイベント） | 離脱を比べる材料がない | 大。過去A/Bでの方向一致率の検証だけになる |
| 過去のA/Bテスト結果 | 方向一致率を測れない | 大。離脱分布の比較だけになる |

層2がない場合の代わりの手：

- **比較の起点を後ろにずらす（推奨）**：「日付と人数を入れて検索した人」から先だけでファネルを比べる。予約意図のある人に絞られ、そこから先の離脱はUIの影響が大きい。
- **行動の類型で代用する**：「1画面で帰った類型」を眺めるだけとみなすなど。
- **意図の比率を1つのパラメータとして合わせる**：手軽だが合わせ込みに注意。

> **次の一手**：A社のアクセス解析で記録されているイベント名の一覧を確認する。確認するのは、画面表示、検索条件（日付・人数の入力）、エラー・空室なしの表示、セッションの終わり方の4点。データ本体の利用申請より手前の作業である。

### 人間の離脱統計に近づける手順

1. 人間のログを、補正用と検証用に分ける（期間・画面・アプリのバージョンのいずれかで）。
2. まず素のまま走らせ、画面ごとの到達率の曲線を人間と並べる。
3. 粗い層から順に、1つずつ調整する。
   1. 構成比の重み付け（走らせ直し不要で一番安い）
   2. 来訪意図の混合比
   3. 行動傾向と離脱条件
   4. プロンプトの文言
4. 補正に使っていないデータで当たるかを確かめる。ここが本当の検証である。

| 合わせる対象 | 判定 | 理由 |
|---|---|---|
| 離脱率の絶対値 | ✗ 目標にしない | 価格・空室・季節など、アプリの外の理由が混ざる |
| 離脱の多い画面の順位 | ○ | どこが悪いかはUIに起因する |
| 新旧バージョン間の離脱の増減の向き | ◎ | リリース前テストで本当に知りたいこと |

落とし穴：

- パラメータを増やせば1つのファネルにはいくらでも合う。補正に使っていない画面や次のバージョンで当たって初めて検証になる。
- AIの離脱には「ボタンを押せなかった」など操作技術の失敗が混ざる。人間の「やめた」とは別物なので、ログで区別して除外する。
- AIの集団は行動がそろいすぎる。同じペルソナを複数回走らせて、ばらつきも人間と比べる。

### 類型化と補正は別の作業

類型は人間のデータだけで機械的に決まる。試行錯誤するのは、類型ごとに人間と同じように動くペルソナの文章を見つける「補正」のほうである。

| 作業 | 何をするか | 使うデータ | 試行錯誤 |
|---|---|---|---|
| ① 類型化 | セッションを行動の特徴（操作数・閲覧件数・検索・どこまで進んだか）で数グループに分け、比率を重みにする | 人間のログだけ | ほぼ不要 |
| ② 補正 | 類型ごとにAIの行動を人間と比べ、ペルソナの文章を直す | 人間のログ＋AIのログ | ここが反復作業 |

- 補正は手探りではない。類型の統計から最初の文章を機械的に書き（例：比較件数の中央値5件 →「4〜6件比較してから決める」）、ずれた部分だけを直す。
- 探す範囲を狭める方法：数値をそのまま書く、その類型の典型的なセッションを匿名化して2〜3件添える、修正案を別のLLMに出させる。最も効果が確実なのは行動例を添える方法。
- 類型の数はAIとの一致度ではなく、人間のデータだけを見て解釈しやすさと安定性で決める。修正回数には上限を設け、検証用データで必ず確かめる。

### 補正は使うモデルごとに必要

同じペルソナの文章でも、モデルやそのバージョンが変われば動き方は変わる。SimGymでも、同じ方式でGemini 3 Flash（画像あり）77%、同（テキストのみ）70%、GPT-OSS（テキストのみ）59%と差が出た。

| 部分 | モデルへの依存 | 扱い |
|---|---|---|
| 類型と比率 | しない | 資産として残す |
| 統計から書いた最初の文章 | ほぼしない | 資産として残す |
| 補正で足した修正、実行設定 | する | モデルごとに作り直す |

- 「モデル名＋バージョン＋ペルソナの文章」を1組で記録する。
- モデル更新に備えて補正手順を自動化し、更新のたびに検証用データで精度を測り直す。
- Amazon研究も主実験はClaude Sonnet 4.5のみ。モデルをまたいだ補正の移り方は先行研究の空白であり、本研究の課題にできる。

### trivagoのデータで予行演習する

社内データが来る前に、trivagoのセッションログで「4層の定義と補正の手順そのもの」を試す。各セッションに、予約サイトへの移動（クリックアウト）まで進んだか、途中で終わったかが残っている。

| 層 | trivagoで作れるか | 使える情報 |
|---|---|---|
| 1. 構成 | ✗ | 属性情報はない（デバイスと国のみ） |
| 2. 来訪意図 | △ | 行き先・観光地での検索から、意図の具体性を推定 |
| 3. 行動傾向 | ○ | 絞り込み、並べ替え、画像・詳細・口コミの閲覧 |
| 4. 離脱条件 | ○ | クリックアウトの有無、終了直前の操作 |

**手順**：セッションを行動の類型に分けて層2〜4のペルソナJSONを作る→類似の宿検索タスクで走らせる→クリックアウト率と操作分布を比べる→補正し、別の日のセッションで当たるか確かめる。成果物は、ペルソナ生成の手順書と、社内ログにそのまま差し替えられるスクリプト。

## 社内データ収集へ進める流れ

申請は「公開データで何が分かり、何が分からなかったか」を示し、分からなかった部分だけを社内データで補う形にする。各段階の結果が、そのまま依頼データ1件ごとの根拠になる。

段階1〜4の結果が、下の依頼データ1件ずつの必要性を示す。

### 申請パッケージの中身

| 依頼データ | 粒度と匿名化（案） | 根拠になる段階 | 使い道 | 合格基準の例（案） |
|---|---|---|---|---|
| 顧客属性の匿名集計 | 集計値のみ、個票なし。10人未満のセルは非表示 | 段階1 | ペルソナの構成比を補正 | 主要属性の構成比の差が公的統計より縮む |
| 過去のA/Bテスト結果 | 施策ごとの2案と勝敗、差の大きさ。30〜50件 | 段階2 | 方向一致率の本番評価 | 素のClaudeより方向一致率が10pt以上高い |
| 画面遷移ログの集計 | 画面ごとの到達数と離脱数、セッションあたり操作数の分布 | 段階3 | 行動分布の比較と補正 | 補正後の分布の距離が補正前より小さい |
| 過去のユーザビリティ調査・問い合わせ | 問題の画面と内容の一覧（個人情報を除く） | 段階4 | 問題検出の再現率の評価 | 主要な問題の半数以上を検出 |

> **件数の目安**：A/Bテスト40件程度だと方向一致率の誤差は±7pt前後ある。10ptの差を示すには、30〜50件以上を依頼する。

### 申請までの進め方

1. 段階1〜4の合格基準を文書にして、着手前に関係者と合意する。
2. 段階1〜4を実施し、結果を「確認できたこと」「公開データでは確認できないこと」に分けて整理する。
3. 確認できないことごとに、必要な社内データを1件ずつ対応させる（上の表）。
4. データ管理部門と匿名化の水準と持ち出し範囲をすり合わせ、申請する。
5. 社内データで本検証を行い、事前に固定した基準で合否を判定する。

## 先行研究まとめ

先行研究の共通理解は、合成ユーザーは「どちらが良いか」の方向はある程度当てるが、差の大きさと人間のばらつきは再現しにくい、というもの。精度を上げる鍵は、ペルソナを対象ドメインの行動データで裏づけること。

| 研究 | 発表 | 主な結果 | 本研究への示唆 |
|---|---|---|---|
| SimAB | arXiv 2026年3月 | 画面の2案をペルソナ付きエージェントに比較させ、結果が既知の過去A/Bテスト47件で正解率67%、確信度の高いケースに限ると83% | 方向一致率という測り方の直接の前例。件数が少ないと信頼区間が広い |
| エージェントによるA/Bテスト（Amazon） | CHI EA 2026 | 実サイト上でエージェントに購買タスクを行わせ、施策の効果の方向は人間と一致。一方で操作数は人間約16に対し約6 | 画面操作型の前例。操作数の偏りを前提に設計する |
| データで裏づけたペルソナのA/B予測 | arXiv 2026年9月 | 属性だけのペルソナは、申込み予測でペルソナなしを下回り（0.30対0.65）、クリック予測では上回った（0.65対0.45）。行動データから作ったペルソナは0.75〜0.80 | 現在の属性ベースのペルソナの限界と、社内行動データが必要な理由の根拠 |
| OPeRA | ACL 2026 | 実ユーザー51名・692セッションのペルソナ付き操作ログ。特定ユーザーの次の操作をLLMが予測できるかを測る基準 | 段階3で使う公開データ。ペルソナの有無で精度が変わるかを確かめられる |
| LOLA | Marketing Science 2025 | Upworthyの見出しA/Bテスト約1.8万件で、プロンプトだけのLLMは2案の勝者を最大65%しか当てられない | 段階2のベースライン。合成ユーザーは実A/Bの代替ではなく候補の絞り込みに使う |
| 合成ユーザーと人間の比較（NN/g） | Nielsen Norman Group | 合成回答はばらつきが小さく、傾向は似るが大きさは一致しない | ばらつきの比を指標に入れる根拠 |
| Nemotron-Personas-Japan | NVIDIA | 日本の公的統計の分布に基づく合成ペルソナ | 現在のペルソナの土台。属性の分布は妥当だが行動の裏づけは含まない |

### SimGym（ペルソナの作り方の手本）

社内データを得た後の到達点の参考になるのが SimGym である。ただし旅行ではなく、ECショップの研究。

| 項目 | 内容 |
|---|---|
| 著者・時期 | Shopify。2026年2月の論文と2026年5月の枠組み論文 |
| 査読 | なし（プレプリント）。自社基盤での自社評価 |
| 方式 | 本番のクリックストリームを行動の特徴で類型化し、購入意図を付け、類型の比率で重み付けしてブラウザ操作エージェントを走らせる |
| 規模 | 50店舗（16か国・11業種）のデザイン変更。旅行業を含むかは未確認 |
| 精度 | カート追加の増減の方向一致率77%（95%信頼区間66〜87%） |
| 重要な結果 | 購入者の類型を外すと一致率は44〜51%に落ち、相関はほぼゼロ。行動データの必要性を示す最も直接的な証拠 |
| 限界 | 単一のEC基盤のみ、評価はカート追加のみ、店舗ごとにその店舗自身のデータでペルソナを作っており、別のアプリへの移植は未検証 |

信頼度は中程度（数字は一次情報で確認済み、ただし査読前・第三者の追試なし）。

### 旅行領域の研究

ここまでの先行研究はすべてEC・Web施策のもの。旅行領域にもペルソナ研究はあるが、旅行アプリの画面操作を人間の離脱データと照合した研究は見当たらない。

| 研究 | 中身 | 本研究との近さ |
|---|---|---|
| Profile-Conditioned Travel User Simulation（NeurIPS 2026掲載） | 大手オンライン旅行プラットフォームのAI旅行計画チャットボット向け。会話ログから行動特性と旅行の好みを書いたプロフィールを作り、人間とLLMの話し方の違いも反映する | ◎ コンシェルジュ・計画支援の手本 |
| Aligning LLM with Humans for Travel Choices（Transportation Science、査読あり） | 実データから旅行者ペルソナを推定し、属性から適切なペルソナを割り当てる（交通手段の選択） | ○ 類型を属性で割り当てる発想は層1と層3をつなぐ参考 |
| Aligning LLM agents with human learning and adjustment behavior | LLMの補正エージェントが旅行者ペルソナを調整する | ○ 補正の自動化の先例 |
| Towards Full Delegation | 旅行計画エージェントの評価用に、54項目に値を無作為に割り当てて合成旅行者を作る | △ 人間のデータと照合していない |

```
EC・Web施策（画面操作×人間データと照合）：SimGym・Amazon・SimAB  → 方式の手本
旅行×対話（会話ログ→プロフィール）      ：Profile-Conditioned Travel   → コンシェルジュ・計画支援の手本
旅行×選択行動（実データ→ペルソナ）       ：Transportation Science       → 類型化の考え方
旅行アプリの画面操作×人間の離脱データ     ：見当たらない                → 本研究の位置
```

## 研究を進める根拠と限界

合成ユーザーによる事前テストは、「明らかに悪い案を落とす選別の道具」としてなら先行研究の裏づけがあり、施策として妥当。効果の大きさの予測と実A/Bテストの代替は未証明である。

### 用途ごとの裏づけ

| 用途 | 先行研究の裏づけ | 判定 |
|---|---|---|
| 2案のどちらが勝つか（方向）の予測 | SimAB 67%（確信度の高いケース83%）、SimGym 77%、行動データペルソナ 75〜80%。素のLLMは最大65% | ○ |
| 明らかな使いにくさ・導線の詰まりの検出 | 方向は人間と一致。ただし操作は浅い（操作数は人間の約4割） | ○〜△ |
| 顧客層ごとの反応差 | 行動データで裏づけたペルソナで改善する例があるが、層ごとの検証は乏しい | △ |
| 効果の大きさ（CVRが何%上がるか） | 再現できない。合成回答はばらつきが小さい | ✗ |
| 実A/Bテストの代替 | どの研究も主張していない | ✗ |

### 精度を決めるのは、過去A/Bテストの件数

社内データには役割の違う2種類がある。信頼性を決めるのは顧客数ではなく、正解として使えるA/Bテストの件数である。

| データ | 役割 | 量の効き方 |
|---|---|---|
| 顧客の行動ログ（画面遷移など） | ペルソナを現実に近づける | 多いほど良い。A社には十分ある見込み |
| 結果が分かっている過去のA/Bテスト | 精度を測る正解 | 件数が信頼性を決める。40件程度で誤差±7pt前後 |

> **未確認**：社内に過去のA/Bテスト結果が何件残っているか。申請前に最初に確かめる。

### 「証明済み」と言い切れない理由

- **論文の質**：多くは査読前のプレプリントか開発者自身の評価で、第三者の追試は乏しい。
- **学習データ汚染**：公開済みの過去テストは、LLMが学習済みの可能性がある。
- **領域の違い**：実証は主にECとニュース見出し。旅行予約は検討期間が長く、価格・空室・季節の影響を受ける。

逆に、A社の社内A/B結果は非公開なので汚染の心配がない。旅行領域での検証そのものに研究上の価値があり、精度が出なくても限界を示す成果になる。

### ペルソナの種類

ペルソナは「何を手がかりに作るか」で分けられる。下に行くほど現実の行動に近く、作るのに必要なデータも重くなる。

| 種類 | 中身の例 | 作る手がかり | Amazon研究の方向一致率（クリック／申込み） | A社での作りやすさ |
|---|---|---|---|---|
| ペルソナなし | 素のLLMにそのまま判断させる | なし | 0.45／0.65 | すぐ可能 |
| 汎用ペルソナ | 「平均的な利用者」1人 | 設計者の想定 | 0.40／0.60 | すぐ可能 |
| 属性ペルソナ | 年代・性別・居住地・職業 | 公的統計、集計値 | 0.65／0.30 | 構築済み（現在の方式） |
| 人物描写ペルソナ | 属性に価値観・趣味・生活の描写を加える | 属性からLLMが生成 | 未検証。行動の裏づけがない点は属性ペルソナと同じ | 構築済み（Nemotronの描写を使う場合） |
| 行動データペルソナ | 閲覧・検索・購入の傾向、よく使う機能 | 実際の行動ログ | 0.75／0.80 | 社内データが必要 |
| 意図付きペルソナ | 「来月の家族旅行の宿を比較中」など来訪目的を持つ | 行動ログから類型と意図を抽出（SimGym） | ―（SimGymではカート追加の方向が77%一致） | 社内データが必要。タスク設計で一部代用できる |
| 個人再現型 | 特定の1人の履歴・アンケートをそのまま持たせる | 個人の記録 | ―（OPeRAが評価の基準を提供） | 個人情報の扱いが重く、当面は対象外 |

### 属性だけのペルソナの結果の読み方

「属性だけのペルソナはバニラに負ける」は言い過ぎ。正確には「申込みのような重い決定の予測では、属性だけでは足りず、逆方向に外しやすい」。

- **実験**：Amazonの研究者が、ECの広告パーツのデザインA/Bテスト40件（クリック率20件・申込み20件）で、ペルソナの作り方ごとに勝敗の方向一致率を比べた。モデルはClaude Sonnet 4.5。
- **数字の中身**：1条件は20件なので、1件で5pt動く。0.30は20件中6件正解、0.65は13件正解。
- **0.30の意味**：当てずっぽう（0.50）より低い。ランダムに外したのではなく、一貫して逆方向を予測したことを示す。
- **著者の説明**：重い決定では行動の裏づけが重要、とだけ述べている。ペルソナなしを下回った理由は論文に明記されていない。
- **推測**：属性だけを与えると、LLMは「50代だから慎重」のような固定観念で理由を補い、集団全体が同じ方向に偏る可能性がある。
- **限界**：1研究、1領域、1モデル、各条20件。正解データは非公開で追試できない。
- **A社への含意**：旅行予約は申込みと同じ「重い決定」側であり、申込みの結果のほうが参考になる。段階2で、属性ペルソナとペルソナなしを自分で比べて確かめる。

## 研究の位置づけと展開

本研究は、ペルソナの作り方をSimGymに、評価の仕方をAmazon研究とSimABに倣う。その上で、先行研究の空白である「旅行アプリ」「離脱条件」「新規アプリへの移植」を独自の検証対象にする。

### 手本にする部分と独自の部分

| 要素 | 倣う先 | 理由 |
|---|---|---|
| ペルソナの作り方（行動ログ→類型→意図→重み） | SimGym | 行動ログから作る方式で最も実証が進んでいる |
| 評価の仕方（方向一致率、事前に固定した基準） | Amazon研究、SimAB | 2案比較の評価として確立している |
| 対話型アプリのペルソナ | Profile-Conditioned Travel | 旅行の対話ログから作る先例 |
| 層4（離脱条件）、新規アプリへの移植、モデルをまたいだ補正 | 独自 | 先行研究の空白で、新規性になる |

### 新規アプリへの適用

ペルソナはテキストなので、skillはどのアプリにも走らせられる。ただし「動く」ことと「当たる」ことは別で、新規アプリでの精度は未検証。

| 適用先 | 先行研究 | 判定 |
|---|---|---|
| 同じアプリの次の試作 | Amazon研究（同じ基盤上の新デザインを予測） | ○ |
| 同じ基盤の別店舗 | SimGym（ただし店舗ごとにその店舗のデータで作成） | △ |
| ログのない新規アプリ | 見当たらない | 未検証 |

移せるのはアプリに依存しない要素だけである。層1・2（誰が、何をしに来るか）は移せる。層3・4は「4〜6件比較する」「予算を2割超えたらやめる」のような抽象的な書き方なら移せるが、画面固有の操作や離脱率の絶対値は移せない。

移植の検証方法：

1. 社内でチャネル移植を試す。Webサイトのログでペルソナを作り、既存アプリのファネルを予測できるかを測る。
2. 新規アプリは公開直後数週間の実ログで答え合わせし、補正する。

### アプリの種類ごとの見込み

| アプリ | 利用者 | 測る指標 | 先行研究 | 見込み |
|---|---|---|---|---|
| 旅行予約（検索→予約） | 顧客 | 離脱・完了率 | SimGym、Amazon、trivagoのデータ | ○ |
| 旅行計画支援 | 顧客 | 計画の完成率、修正回数 | Profile-Conditioned Travel | △ |
| コンシェルジュ（対話） | 顧客 | 解決率、往復回数、途中放棄 | Profile-Conditioned Travel、対話システムのユーザーシミュレーション | △ |
| 旅行営業支援（社内向け） | 社員 | 作業時間、完了率 | 少ない | △〜✗（本物の利用者に直接試してもらう方が早く確実） |

### 汎用skillの構成

```
共通部分（全アプリで使い回せる）    アプリごとに必要な部分
├─ 実行エンジン（画面操作・対話）    ├─ 利用者の母集団（ペルソナ）
├─ ログ形式                         ├─ タスク
├─ 集計                             ├─ 指標
└─ 評価（人間との比較）              └─ 正解データ（人間のログ）
```

最初から全種類に対応させると、どれも検証できないまま広がる。ログと先行研究がそろう旅行予約で検証を1周回してから横に広げる。展開の順番は「同じアプリ → チャネル移植 → 新規アプリ」。

### 論文化の見込み

先行研究の空白に当たる点が少なくとも4つあり、論文化できる見込みは高い。

1. 旅行アプリの画面操作を、日本の顧客の実際の離脱データと照合する
2. 離脱条件（層4）を持たせたペルソナの効果
3. 既存アプリから別の画面体系への移植（Web→アプリ、新規アプリ）
4. モデルを替えたときに補正が保たれるか

**条件**：A社のデータを使った結果の公開には、集計値のみでも社内の公開承認が必要。公開データ（trivagoなど）で再現できる部分を用意する。「旅行領域では効かなかった」という結果も、ワークショップや国内学会で発表できる。
