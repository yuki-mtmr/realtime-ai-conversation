# 旅行アプリ施策の事前評価: 研究計画（具体版）

作成日: 2026-11-16 / 前提資料: [synthetic-user-research-protocol.md](./synthetic-user-research-protocol.md)（進め方の規約）、[synthetic-user-research.md](./synthetic-user-research.md)（先行調査メモ）

## このメモを読む Claude へ

- 規約（protocol）の §3「研究の問い」を、依頼者の回答で埋めた計画。規約の R1〜R9 と §4〜§7 はそのまま有効で、このメモはその適用例である。
- 「確定」と書いた項目は依頼者の発言に基づく。それ以外の設計・件数・閾値は**作成者の提案**で未承認。着手時に依頼者と確定すること。
- 作成者は依頼者のデータを見ていない。件数や形式に関する記述は全て仮定で、§2 の棚卸しで置き換える。
- **このリポジトリは公開されている。** 実データ、集計値、施策の具体的内容、事業者名をここに置かない（§8）。

## 結論

1. **この研究は真値を持っている。** 過去の AB テストは、結果が既知の問題集である。規約 §4 の「真値の作り方」のうち最も強い手段が最初から使える。ポケカで言えばリーダーボードに当たる。
2. **ただし問題集は有限で、使うたびに減る。** 過去テストの結果を見ながら構成を調整すると、その結果に合わせ込んだだけの仕組みができる。最初にやることは、新しい側のテストを保留分として分け、封をすることである。
3. **過去テストの本数が、言える主張の上限を決める。** 20 本なら「75% 当たった」の 95% 信頼区間は 53〜89% で、基準線との優劣はほぼ言えない（§4）。本数を数えるまで、目標の数値を置かない。
4. **比べる相手は「偶然」ではなく「もっと安い方法」。** 素の LLM、過去テストから作る単純な統計モデル、担当者の事前予測に勝てなければ、顧客模倣エージェントを作る理由が無い（§5）。
5. **エージェントと skills は、同じ問題集で比べる 2 つの構成として扱う。** どちらも弱い構成 1 回の結果で閉じない（規約 R2・R3）。

## 1. 確定していること

| 項目 | 内容 |
|---|---|
| 対象 | 旅行アプリ |
| 目的 | リリース前に施策を評価するシステムの開発 |
| 手段の候補 | 顧客を模倣したエージェント、または skills の利用 |
| 手持ちのデータ | アンケート、過去の AB テスト、顧客の属性データ |

## 2. 最初に数えること（未確定）

実装の前に、依頼者と次を埋める。ここが埋まらない主張は §3 から外す。

| 確認すること | なぜ必要か |
|---|---|
| 過去 AB テストの本数と実施時期 | 主張の上限と、保留分の大きさが決まる |
| 各テストに残っている記録（案ごとの画面・文言、主要指標、標本数、差と信頼区間、属性別の結果） | 案の内容が再現できないテストは問題として使えない。属性別の結果が無ければ P3 は検証できない |
| 施策の種類の内訳（文言、配置、価格・特典、導線、機能追加など） | 種類ごとに当てやすさが違う。偏っていれば、結論はその種類に限る |
| アンケートの時期・設問・回答数、顧客 ID で属性と結びつくか | 結びつかなければ、個人単位のペルソナは作れず、集団の分布からの生成になる |
| 担当者の事前予測の記録があるか | 最も重要な基準線の 1 つ。無ければ今後のテストから記録を始める |
| データを外部の API に送れるか、匿名化の要件 | 構成の選択肢（外部モデルか社内実行か）が決まる |
| 結果の使い道（実テストにかける案の絞り込みか、出荷判断か） | 評価指標が変わる。出荷判断への利用は、先行調査の範囲では支持する資料が無い |
| 今後、新しい AB テストを実施できるか | できれば、事前に予測を登録してから結果を見る検証が可能になる（最も強い証拠） |

## 3. 検証する主張（提案）

件数と閾値は §2 の棚卸し後に確定する。各主張は規約 §6 の書式で事前に登録する。

- **P0（計測器）**: 効果が大きく明白だった過去テストで勝者を当て、同一案どうしの比較で「差あり」と言わない。P0 を通過するまで P1 以降の結果を論じない。
- **P1（方向）**: 保留分のテストで、勝者（勝ち・負け・差なしの 3 値）の正答率が §5 の基準線を上回る。
- **P2（優先順位）**: 予測した効果の順位と、実測の効果の順位が相関する。使い道が「案の絞り込み」なら、これが本命の主張になる。指標の例: 予測上位の半分だけを実施したと仮定したときの実測効果の合計を、無作為に半分選んだ場合と比べる。
- **P3（属性別の差）**: 属性別の反応の違い（どの層に効いたか）を当てる。属性別の結果が記録されているテストに限る。
- **P4（データの寄与）**: アンケート、属性データ、過去テストの事例を 1 つずつ抜いたとき、P1・P2 の成績がどう変わるか。
- **P5（構成の比較）**: 顧客模倣エージェントと skills 型（データ要約を参照して評価する構成）を、同じ問題・同じ条件で比べる。

効果の大きさそのものの予測（何 % 上がるか）は、先行調査の範囲で成功例が見つかっていない。主張に入れる場合は新規研究として扱い、P2 が支持された後に置く。

## 4. 真値の整備

### 過去テストの台帳

テストごとに 1 行。入力側（予測させるときに渡す情報）と正解側を別のファイルに分け、正解側を実行系から読めない場所に置く。

- 入力側: テスト ID、実施日、各案の内容（当時の画面や文言）、対象者の条件、主要指標の定義
- 正解側: 各案の標本数、差と信頼区間、判定（勝ち・負け・差なし）、属性別の結果

### 正解そのものの不確かさ

- AB テストの結果にも誤差がある。信頼区間が 0 をまたぐテストを「差なし」とするか問題から外すかを、結果を見る前に決める。
- 有意だったテストの効果量は、大きめに出ている可能性がある（有意なものだけ選ぶと過大になる）。効果量の予測を評価するときは、この偏りを考慮する。
- 標本が小さく結論が出なかったテストは、「差なし」の正解としては弱い。別枠で数える。

### 漏洩の点検

ポケカの「教師データの汚染」に当たる。次を全て確認してから測る。

- 入力に、結果・事後の考察・「採用された案」の情報が入っていない。案の並び順と名前（A/B、現行/新案）から勝者が推測できないよう、順序と呼び名を入れ替える。
- アンケートや属性データが、予測対象のテストより後に取られていない。後のデータは、施策の結果を反映している可能性がある。各テストについて、その実施日より前のデータだけを使う。
- 現在公開されているアプリの画面は、過去に勝った案である可能性が高い。モデルが公開情報から現行の画面を知っていると、勝者を推測できる。入力に現行かどうかを示さず、点検として「どちらが現行に見えるか」をモデルに聞き、偶然を超えて当たるなら漏洩として扱う。

### 分割

- **時系列で分ける。** 古い側を開発用、新しい側を保留分とする。無作為に分けると、後のテストの知見で前のテストを当てる形になる。
- **保留分は封をする。** 開ける回数を事前に決める（提案: 1 回、多くて 2 回）。開けた回数と、そのとき見た数値を台帳に残す。
- **開発用での成績は結論に使わない。** 構成選びに使った問題での正答率は、過大に出る。

### 本数と言えること

正答率 75% 前後を観測したときの 95% 信頼区間（Wilson 法）:

| 保留分の本数 | 観測 | 区間 |
|---|---|---|
| 20 | 15/20 | 53〜89% |
| 50 | 38/50 | 63〜86% |
| 100 | 75/100 | 66〜82% |

基準線が 60% 台なら、20 本では優劣を言えない。本数が少ない場合の手当て:

- 同じテストで基準線と本命の両方に予測させ、当たり外れが食い違ったテストだけを数える（ペア比較）。
- 属性別の結果を問題として数える（P3）。ただし同じテスト内の属性別結果は独立ではないので、テスト単位でまとめて誤差を出す。
- 今後のテストで、結果が出る前に予測を登録する。本数は少しずつしか増えないが、漏洩の心配が無い。
- それでも足りなければ、結論は「判定不能、必要な本数は N」で終える（規約 §6）。

## 5. 基準線のはしご

下から順に実装し、同じ問題・同じ条件で比べる。隣り合う段の差が、その段で足した要素の寄与になる。

| 段 | 構成 | 何が分かるか |
|---|---|---|
| B0 | 偶然、および開発用での多数派（例: 常に「差なし」） | AB テストは差なしが多い。多数派を答えるだけで高い正答率になり得る |
| B1 | 素の LLM に案の内容だけ渡して予測させる | モデルの一般知識だけで当たる分 |
| B2 | 開発用の過去テストから作る単純な統計モデル（施策の種類ごとの平均、似た施策の結果の参照） | LLM を使わずに当たる分 |
| B3 | 担当者の事前予測（記録があれば） | 現状の意思決定の精度。これに勝てるかが実用上の基準 |
| B4 | LLM にアンケートの集計と属性の分布を文脈として渡す（skills 型） | 自社データを渡すことの寄与 |
| B5 | 属性とアンケートに根拠づけた顧客ペルソナを多数作り、各自に案を選ばせて集計する（エージェント型） | 個人単位の模倣の寄与 |
| B6 | B5 に実画面の操作を加える | 操作の寄与 |

- B5 や B6 が B1・B4 に勝てなくても、「顧客模倣は使えない」とは書かない。「この構成では、個人単位の模倣が上積みになっていない」と書き、試していない構成を列挙する（規約 R1・R5）。先行調査メモ §3 に、ペルソナなしが勝った報告がある。
- 逆に B1 が既に十分当たるなら、複雑な仕組みは不要という結論もあり得る。それも成果として記録する。
- ペルソナ 100 体は 100 人分の標本ではない（規約 §4）。誤差はテストの本数で出す。

## 6. 段階と通過条件（提案）

| 段 | やること | 通過条件 |
|---|---|---|
| 0 | §2 の棚卸し。台帳の作成と時系列分割。保留分に封。規約 §8 の一次情報を読む（特に SimAB、Upworthy の反証、Statistical Foundations）。API 費用の見積もりと承認 | 主張 P0〜P5 が件数・閾値つきで登録されている |
| 1 | B0〜B2 を開発用で実行。漏洩の点検 | 漏洩の点検を通過。B0 の正答率が分かり、目標の置き方が決まる |
| 2 | P0。明白なテストと同一案どうしの比較 | 明白なテストをほぼ全て当て、同一案どうしで差を言わない |
| 3 | B4・B5 を開発用で作り、1 要素ずつ変えて改善。開発用の中をさらに 2 つに分け、選ぶ用と確かめる用にする | 確かめる用で、基準線との差が再現する |
| 4 | 保留分を開け、事前登録した構成 1〜2 個だけを評価 | P1〜P5 に支持・不支持・判定不能が付く |
| 5 | 今後の AB テストで、結果が出る前に予測を登録して照合 | 的中と外れを具体例つきで記録。これが無い限り「今後の施策にも当たる」とは書かない |

段 3 が長引いても、保留分を覗いて方向を確かめない。確かめたくなったら、開発用の分割をやり直す。

## 7. この研究でポケカの型が現れる場所

| ポケカで起きたこと | この研究での現れ方 | 防ぎ方 |
|---|---|---|
| 小規模な 1 回の試行で本道を閉じた | 少数のペルソナ・数本のテストで「顧客模倣は当たらない」と結論する | 規約 R2・R3。P0 を通過していない構成の結果は故障として扱う |
| ローカルの勝率が本番に転移しなかった | 開発用で当たる構成が、保留分や今後のテストで当たらない | 時系列分割、保留分の封、段 5 |
| 改善を 3 段積んだら祖先より弱かった | 開発用への合わせ込みを重ね、素の LLM（B1）より悪くなる | 改善のたびに B1・B2 と直接比べる。直前の版とだけ比べない |
| 一致率が上がったのに実戦で逆効果 | アンケート回答の再現率が上がっても、AB テストの予測は良くならない | アンケートの再現は中間指標として扱い、完了条件にしない |
| 測定器の不具合で「効かない」と誤判定 | データの結合ミスや渡し漏れで、属性やアンケートが実際には使われていない | 要素を抜いたとき出力が変わることを、成績を見る前に確認する |
| 依頼者の指摘を AI が退けた | 依頼者の「この層はこう動く」という知見を、データに無いとして退ける | 規約 R9。知見を仮説として登録し、最も安い実験で試す |

## 8. データの扱い

- このリポジトリは公開。置くのは方法と書式だけにする。実データ、集計値、施策の内容、事業者や顧客を特定できる情報は置かない。台帳と実験記録は非公開の場所に作る。
- 顧客の属性データとアンケートは個人に関する情報である。外部の API に送る前に、所属先の規程と依頼者の承認を確認する。承認が無い間は、集計した分布だけを使う。
- ペルソナは集団の分布から生成し、実在の個人を再現しない。個人単位で結びつける場合は、匿名化の要件を先に確認する。

## 9. 完了条件と停止条件

規約 §6 に加えて、この研究では次を完了条件にしない。

- 開発用テストでの正答率
- 保留分を複数回開けたうちの最良の値
- アンケート回答の再現率
- ペルソナの人数、生成したレポートの量

停止条件: 費用と期間の上限に達したとき。保留分を予定回数開けたとき。P0 が直らないとき（故障の内容を記録して止める）。

## 10. 最初の 1 週間（提案）

1. §2 の表を依頼者と埋める。
2. 台帳を作り、入力側と正解側を分け、時系列で分割して保留分に封をする。
3. B0（多数派）の正答率を開発用で出す。
4. 規約 §8 の一次情報のうち 3 本を読み、評価方法・件数・基準線を抜き出して、P1〜P5 の件数と閾値を確定する。
5. B1（素の LLM）の費用を見積もり、承認を得て開発用で実行する。漏洩の点検を同時に行う。

この時点で、過去テストの本数、多数派の正答率、素の LLM の正答率が揃う。本命の構成の設計は、この 3 つを見てから始める。

## 11. このメモの限界

- 作成者は依頼者のデータを見ていない。本数が十分にある前提で書いた箇所は、§2 の結果で書き直す必要がある。
- 件数・閾値・保留分を開ける回数は提案で、根拠となる測定は無い。
- 「skills の利用」は、先行調査メモ §4 にある Claude Code 向け skill のように、データ要約と評価手順を参照して LLM に評価させる構成と解釈した。依頼者の意図と違えば §5 の B4 を置き換える。
- 過去の実験結果を LLM に予測させる研究には、先行調査メモに載っていないものもある（例: 社会科学実験の結果予測）。作成者は今回それらを再確認していない。段 0 で検索して補うこと。
